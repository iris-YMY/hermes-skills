# XHS Publish & Comment Operations

This skill covers all Xiaohongshu publishing workflows and comment management, using Hermes browser tools (`browser_navigate`, `browser_snapshot`, `browser_console`, `browser_click`, `browser_type`).

---

## PART A: PUBLISH FLOWS

### 0. Overview

**Publish types:**
- Image-text (图文) — recommended default
- Video (视频)
- Long-form article (长文)

**Three elements (all must be ready before publish):**
1. Cover image
2. Title
3. Body text

### Pre-Publish Checklist (Mandatory)

Before any publish action, verify:

- [ ] Cover image is generated/uploaded and visible
- [ ] Title is filled and ≤20 characters (check `xx/20` counter)
- [ ] Body text is filled with content
- [ ] Hashtags/topics are appended to body
- [ ] `browser_snapshot` confirms all three elements are present
- [ ] User has been shown a preview and confirmed

---

### 1. Image-Text Publish (Recommended Default)

#### 1.1 Standard Image-Text Upload

1. Navigate to publish page: `browser_navigate` to `https://creator.xiaohongshu.com/publish/publish`
2. Verify page loaded: `browser_snapshot` — confirm "上传图文" tab is active
3. Upload first image / multiple images
4. Fill title: `browser_type` into title field (recommend ≤20 chars)
5. Fill body: `browser_type` into body text area
6. Append hashtags/topics at end of body
7. Verify three elements: `browser_snapshot` — confirm cover/title/body all present
8. **STOP at publish button** — wait for user confirmation

#### 1.2 Image-Text with Text Overlay (Big-Text Poster / 大字报)

1. Navigate to publish page
2. Click "文字配图" (text overlay) option
3. Input cover text content
4. Click "生成图片" (generate image)
5. Select template style on template page, click "下一步" (next)
6. On edit page, fill: title, body, hashtags
7. Verify three elements, stop at publish button for user confirmation

#### 1.3 Half-Prepublish (No Actual Publish)

Satisfies these conditions:
- Cover image generated (or uploaded) ✓
- Entered edit page ✓
- Title and body filled ✓
- Stopped at publish button (visible but not clicked) ✓

#### 1.4 Image-Text Upload with Externally Generated Cover

For covers generated by gpt-image-2 or other external tools:

1. Confirm cover image file exists locally (recommend PNG/JPG)
2. Copy image to a temporary accessible path (e.g., `/tmp/hermes-uploads/`)
3. Navigate to publish page, click "上传图片" (upload image)
4. Upload cover image via file input
5. Confirm entry to edit page (image edit area + title/body input fields visible)
6. Fill title, body, hashtags
7. **Pre-publish validation:**
   - Title length check: `≤20` (if `xx/20` shows overflow, compress first)
   - All three elements present (cover/title/body)
8. Stop at publish button, wait for user confirmation

---

### 2. Video Publish

1. Navigate to publish page
2. Switch to "上传视频" (upload video) tab
3. Upload video file
4. Fill cover/title/body
5. Verify visibility scope and settings
6. Stop before publish for user confirmation

### 3. Long-Form Article Publish

1. Navigate to "写长文" (write long-form) page
2. Create new or import from link
3. Fill long-form title and body structure
4. **Caution:** If user's goal is image-text, avoid accidentally entering long-form flow

---

### 4. Common Issues & Error Handling

| Issue | Solution |
|-------|----------|
| Accidentally entered long-form | Go back to publish page, switch to "上传图文" |
| Draft shows default video | Switch to "图文笔记" tab before editing |
| Title exceeds limit (`xx/20` overflow) | Compress title immediately |
| Only cover done, no text | Must complete title AND body before publish |
| Web detail page requires QR scan | Handle comments via notification page; use app if needed |
| Duplicate upload entry (double tab) | If first entry fails, try second entry and `browser_snapshot` to verify |
| File upload path error | Ensure file is in accessible temp path, copy first then upload |
| Element stale on publish click | `browser_snapshot` to refresh refs; if still fails, prompt user to manually click "发布" |

## PART B: COMMENT OPERATIONS

### 0. Goals & Principles

- **Goal:** First accurately check, then reply per user instructions
- **Default: checking ≠ auto-replying**
- Reply actions must follow: align target → input text → send
- Default: send only 1 reply per turn (unless user explicitly requests batch)

### 1. Check Flow (Default Execution)

1. Navigate to `/notification`, enter "评论和@" (Comments and @)
2. Scrape latest comments: username, comment text, timestamp
   - Use `browser_console` to extract comment data from the page
   - Use `browser_snapshot` to visually verify comment list
3. Output check results:
   - New comment count
   - Latest 3-5 comment summaries
   - High-risk signals (abuse, phishing, external link bait, obvious violations)
4. Wait for user confirmation before replying

### 2. Notification Page Reply SOP (Preferred)

1. Click "回复" (reply) entry on the target notification row (don't click top search bar)
   - Use `browser_click` on the reply button for the specific notification
2. **Verify** input box placeholder shows `回复 <username>` (unique alignment proof)
   - Use `browser_snapshot` to confirm placeholder text
3. Input reply text using `browser_type` (character-by-character typing preferred)
   - Do NOT default to form-fill methods — some environments require specific field arrays
   - If `browser_type` fails, try `browser_console` to set input value directly
4. Before sending, re-confirm placeholder hasn't drifted
5. Click red "发送" (send) button using `browser_click` (don't use Enter key)
6. After sending, confirm input box disappeared/cleared via `browser_snapshot`

### 3. In-Post Reply SOP (Fallback)

Use when notification page reply is unavailable:

1. Open post detail page comments section via `browser_navigate`
2. Lock target comment (username + comment key fragment)
3. Click "回复" under that specific comment via `browser_click`
4. Verify `回复 <username>` appears via `browser_snapshot`
5. Input text and send
6. Verify success, then proceed to next comment

### 4. Risk Controls & Rate Limiting

- **Default one-send-per-turn:** Only send 1 reply per interaction turn
- **Consecutive reply interval:** 8-15 seconds between replies (user may explicitly request ~5s for speed)
- **Immediate stop triggers** — halt and report when any of these appear:
  - "评论过于频繁" (comments too frequent)
  - "操作过快/操作频繁" (operation too fast/frequent)
  - "请稍后再试" (please try again later)
  - "发送失败/网络异常" (send failed/network error)

### 5. Length & Content Constraints

- Reply length: ≤280 characters (platform limit ~300 chars)
- If too long: compress first, then consider splitting into multiple replies
- **Prohibited:**
  - Fabricating personal experiences
  - Implicit promises (e.g., "I'll definitely write a tutorial later")
  - Making delivery promises unless user explicitly requests

### 6. Common Comment Failures

| Failure | Solution |
|---------|----------|
| Accidentally clicked search bar | Click blank area to dismiss, re-locate notification row |
| Reply target drift | If placeholder doesn't match, cancel and restart |
| Two consecutive send failures | Stop automation, switch to manual confirmation |
| Input error "fields required" | Switch to `browser_type` and retry |

## PART C: RUNTIME RULES (Hermes Browser Adapted)

### C.1 Token & Snapshot Constraints

- Prefer `browser_console` for targeted data extraction; reduce unnecessary full-page dumps
- Only take `browser_snapshot` at key checkpoints:
  - Login confirmation
  - Arriving at publish page
  - After filling content
  - Pre-publish pause
- Avoid full-page snapshots unless user requests full-page archival
- Reuse same tab/session where possible
- Each action retries at most once; on second failure, switch to stable path and report
- Record key evidence: account name, page state, button visibility, character counts

### C.2 Browser Stability Rules (Highest Priority)

- Use Hermes browser tools exclusively: `browser_navigate`, `browser_snapshot`, `browser_console`, `browser_click`, `browser_type`
- Before each action, confirm the target tab is active
- If `no tab is connected` or similar errors appear, re-navigate and retry
- After 2 consecutive click/navigation failures, switch to stable path (e.g., `browser_console` + DOM manipulation instead of direct clicks)
- Never blind-retry the same failing action

### C.3 Search & Browse Constraints

1. Only enter posts from search results page — never navigate directly to `/explore/<id>`
2. Default: skip own account's content (avoid self-browsing)
3. After entering a post, verify: not 404, comments/engagement visible, title/author identifiable
4. Entry method: click card body, avoid clicking avatar/author name (prevents wrong navigation)
5. If comment input is `contenteditable` or `p.content-input`, trigger input events before sending
6. After two click failures or 404s, return to search page and try next result

### C.4 Recovery & Degradation

- If search page structure changes, `browser_snapshot` to update selectors before continuing
- Reuse already-open tabs for key pages (creator page, explore page, user page)
- Before proceeding past an anomaly, tell user "reached exception point"
- Publish page critical action failures:
  1. `browser_snapshot` to refresh element references
  2. Retry same action at most once more
  3. If still failing, switch to stable path (alternative entry / user manual final click)
- Carousel image extraction: never take first `.img-container`; always use `.swiper-slide-active:not(.swiper-slide-duplicate) .img-container img`
- After image extraction, verify URL key segment matches expected cover
- Image-to-image output: if user reports "too similar", switch to style-only prompt and regenerate
