# 基金投资 SOP

## 用户画像
- 风险偏好：平衡型（最大可承受回撤15%）
- 月投入：¥2,000（基础¥1,000 + 机会性加仓¥1,000）
- 年收益目标：20%
- 目标权益占比：50-60%

## 一、建仓 SOP

### 1.1 选基五维评估
| 维度 | 权重 | 标准 |
|------|:---:|------|
| 业绩 | 30% | 近3年同类前1/3 |
| 费率 | 15% | 管理费+托管费<1.5% |
| 基金经理 | 25% | 从业3年+，规模>10亿 |
| 持仓质量 | 20% | 行业分散，个股集中 |
| 回撤控制 | 10% | 最大回撤<同类平均 |

### 1.2 建仓方式
| 市场状态 | 估值分位 | 方式 |
|---------|:------:|------|
| 低位 | <30% | 分2-3次买入 |
| 震荡 | 30-70% | 分4-6次买入 |
| 高位 | >70% | 定投方式 |

### 1.3 新建仓通知
用户提供：代码+名称+金额+买入原因
→ 记录到持仓清单，开始每日跟踪

## 二、持仓管理 SOP

### 2.1 日常监控（agent执行）
- 每日14:30推送涨跌分析
- 异常波动预警（单日涨跌>3%）
- 连涨/跌5天以上提醒

### 2.2 定期复盘
| 周期 | 内容 |
|------|------|
| 每周 | 周涨跌排名+操作回顾 |
| 每月 | 月度收益+资产配置检查+新基金推荐 |
| 每季 | 基金体检（换经理/持仓变化） |
| 每年 | 年度总结+下年策略 |

### 2.3 再平衡规则
某类资产偏离目标>10% → 触发再平衡
卖出占比过高的，买入占比过低的
频率：至少每季度一次

## 三、加仓 SOP

### 3.1 加仓触发条件
| 条件 | 操作 | 数据来源 |
|------|------|---------|
| 单只回撤>10%（绝对） | 加仓10-20% | portfolio.json盈亏 |
| 指数单日跌>2% | 紧急加仓5-10% | 大盘数据 |
| PE<历史30%分位 | 分批加仓 | 用户截图 |
| 定投日期 | 按计划加仓 | 日历 |

### 3.2 加仓频率控制（防过度加仓）

**冷却期规则：**
- 同一基金加仓后 **7天内不再重复提醒**
- Agent 需在 portfolio.json 的 `meta` 中记录每只基金上次加仓日期：`"last_add_dates": {"013180": "2026-07-21"}`
- 播报时检查：距今 < 7天 → 不列入「今日必做」，可在详细报告中注明"冷却中，下次可加: M/D"

**月度加仓上限：**
- 单只基金月度加仓（非定投）不超过 **¥300**
- Agent 需在 portfolio.json 的 `meta` 中记录月度加仓金额：`"monthly_add_amounts": {"013180": 200}`
- 每月初（或截图校准时）清零

**极端跌幅暂停：**
- 单只浮亏 > 15% → **暂停加仓**，等待企稳再评估
- 企稳标准：连续3天不再创新低，或单日反弹 > 2%
- 暂停期间在详细报告中标注"⏸️ 等待企稳"，不列入「今日必做」

### 3.3 金字塔加仓法
第1次：1份 → 继续跌5%：2份 → 继续跌5%：3份

## 四、减仓 SOP

### 4.1 减仓触发条件（双维度）

**维度A：绝对收益止盈**（看持仓盈亏）
| 条件 | 操作 | 来源 |
|------|------|------|
| 盈利>30% | 减仓20-30% | portfolio.json |
| 盈利>50% | 减仓30-40% | portfolio.json |
| 达目标收益率 | 按目标减仓 | 用户设定 |
| 基本面变差 | 减仓50%+或清仓 | 经理变更/规模缩水 |

**维度B：动量信号减仓**（看近期表现，详见fund-portfolio-analysis）
| 条件 | 操作 |
|------|------|
| 30日涨幅>8% 且 回撤>12% | 减仓30-40%（涨太多+波动大） |
| 30日涨幅>5% 且 回撤>10% | 减仓20-30%（锁利润） |
| 30日跌幅>8% 且 商品/避险类 | 减仓20-30%（高位回撤锁利） |

**特殊规则**
- 债券型基金：持有不动（压舱石），除非基本面变差
- 小幅回调<5%且板块长期看好：持有，可定投加仓

### 4.2 回收资金分配
30%→债券基金 / 30%→现金留存 / 40%→回补或新机会

### 4.3 组合健康度检查（每季度）
- 权益类占比：<60%，否则波动过大
- 同板块基金数：≤3只，否则关联风险高
- 债券配比：≥20%，否则缺乏压舱石
- 黄金/商品：10-15%

## 五、清仓 SOP

### 触发条件
- 连续2季度排名后1/3
- 基金经理更换
- 规模<2亿（清盘风险）
- 达目标收益（翻倍）
- 流动性需求

## 七、持仓数据管理（portfolio.json）

持仓明细存储在 `/home/ubuntu/.hermes/profiles/finance-master/portfolio.json`，不存入 memory。
- **更新时机**：用户发持仓截图时（每周五）或操作后告知时
- **Cron Job 读取**：所有定时任务从 portfolio.json 读取持仓，不硬编码
- **Schema**: 见 `references/portfolio-json-schema.md`

### 月报推荐基金管理（recommended_funds.json）

路径：`/home/ubuntu/.hermes/profiles/finance-master/recommended_funds.json`

**用途**：每月1号月报推荐2-3只新基金 → 写入此文件 → 每日14:30播报读取并跟踪建仓时机。

**Schema**:
```json
{
  "meta": {
    "report_date": "2026-07-01",
    "report_month": "2026-07",
    "source": "每月新基金推荐 cron job"
  },
  "recommended": [
    {
      "code": "000834",
      "name": "大成纳斯达克100ETF联接(QDII)A",
      "type": "QDII-指数型",
      "plan": "首笔买入¥200（7月第2周），后续每周四定投¥50",
      "budget": 400,
      "status": "pending",
      "added_date": "2026-07-01",
      "notes": "海外配置，分散A股单一市场风险"
    }
  ]
}
```

**Status 生命周期**: `pending` → `building`（首笔已买）→ `completed`（按计划建仓完毕）/ `expired`（月末未建仓）/ `cancelled`（放弃）

**建仓信号阈值（每日播报使用）**:

| 信号 | RSI(14) | 7日涨幅 | 判定 | 操作 |
|------|---------|---------|------|------|
| ✅ 适合建仓 | <40 且近低点 | <5% | 按计划金额首笔买入 |
| ✅ 适合建仓 | 40-60 且 <MA20 | <5% | 按计划金额首笔买入 |
| 🟡 减半建仓 | 60-70 | <10% | 首笔金额减半 |
| 🔴 暂停建仓 | >70 | >10% | 等回调到 RSI<60 |
| 🔴 暂停建仓 | 任意 | >15%（30日）| 涨幅过大 |
| ✅ 加码建仓 | <50 且单日跌>3% | — | 首笔×1.5 |

**月报→每日联动流程**:
1. 月报 cron（每月1号10:00）→ 推荐基金 → 写入 recommended_funds.json
2. 每日播报 cron（14:30）→ 读取 recommended_funds.json → 对 pending/building 基金拉数据+判断信号
3. 基金出现在 portfolio.json holdings 中 → status 改为 completed
4. 月末（report_month < 当前月份）→ 未建仓的标记 expired

### 交易流水追踪（transactions + pending_transactions）

portfolio.json 包含两个交易数组：

**`pending_transactions`** — 已提交但未确认（T+1 前）
```json
{"date": "2026-06-30", "type": "buy", "code": "004814", "name": "中欧红利", "amount": 150, "note": "逢低补仓，预计7/1确认"}
```

**`transactions`** — 已确认的交易（份额到账后）
```json
{"date": "2026-06-29", "type": "sell", "code": "007817", "name": "国泰通信设备", "amount": 4460, "note": "减仓40%"}
```

**T+1 更新流程：**
1. 用户告知操作 → 写入 `pending_transactions`，**不改 holdings**
2. 下一个交易日确认份额后 → 从 pending 移入 `transactions` + 更新 `holdings` 的 amount/cost
3. 每周五截图校准时，检查 pending 是否全部确认

### 收益率计算（两种口径）

**1. 持仓收益率**（仅看当前持仓）
```
持仓收益率 = (当前持仓总市值 - 当前持仓总成本) / 当前持仓总成本 × 100%
当前持仓总市值 = Σ(持有份额 × 最新净值/估值)
持有份额 = 持仓金额 / 昨日净值（反推）
```

**2. 全局收益率**（含已实现盈利，年底用这个）
```
全局收益率 = (当前总市值 + 累计减仓回收 - 历史累计总投入) / 历史累计总投入 × 100%
历史累计总投入 = 当前持仓总成本 + 已减仓部分的对应成本
已减仓对应成本 = 减仓后剩余成本 / 剩余比例 - 减仓后剩余成本
```

### 持仓成本追踪
成本计算方式：**加权平均价**（非指数倍增长）
```
持仓成本 = 总投入金额 ÷ 总持有份额
```
每次加仓/减仓后必须重新计算 portfolio.json。

## 八、互动规范

### 用户需提供
- 买入/加仓/减仓/清仓：代码+金额（操作后立即告知）
- 每周持仓截图（周五16:00周报后发，用于数据校准）
- 每月估值截图（且慢/蛋卷APP → 估值页面）
- 风险偏好/资金计划/大额支出变化

### 月报推荐基金 → 每日播报联动
- 每月1号月报推荐2-3只新基金 → 写入 `recommended_funds.json`
- 每日14:30播报自动读取该文件，对每只 pending/building 状态的推荐基金：
  - 拉取实时估值+近30日净值
  - 计算 RSI/收益率/回撤/均线
  - 判断建仓信号（✅适合/🟡观望/🔴暂停）
  - 结合计划建仓时间窗口给出具体操作建议
- 基金买入后 status 改为 "completed"；月末未建仓的标记 "expired"
- 建仓信号阈值：RSI>70 或 7日涨>10% → 🔴暂停；RSI<40 且近低点 → ✅建仓

### agent输出
- 每日14:30：涨跌分析+**具体操作建议**（基金+操作+金额）+紧急提醒
  - **🔴 今日必做**（报告最顶部，所有其他板块之前）：只列今天必须执行的操作。可以观望的、建议等几天的、不急的一律不放。每条必须具体到：基金代码+名称、操作方向（买入/卖出/加仓/减仓）、金额。如果今天无需操作，写"✅ 今日无需操作，继续观望"
  - **周四定投日特殊处理**：结合本周（周一至今）走势，按智能定投规则调整每只基金的定投金额，每条说明涨跌幅→理由→实际金额
- 每周五16:00：周报汇总+定投执行情况
- 每月1号10:00：月报+新基金推荐+投资计划
- 紧急：大幅波动即时提醒

### 与todo系统联动
基金相关任务（如搭建回测系统）可通过 `~/.hermes/scripts/todo_manager.py` 记录，带截止日期：
```bash
python3 /home/ubuntu/.hermes/scripts/todo_manager.py add "任务内容" --due 2026-09-30 --priority medium
```
注意：必须用绝对路径 `/home/ubuntu/.hermes/scripts/todo_manager.py`，不能用 `~/.hermes/` 形式（finance-master profile 的 home 目录不同）。

## 数据诚信铁律（不可违反）
1. **禁止编造**：所有支撑分析模型的数据如无法获得，必须如实告知用户"该数据暂无"，并写明"无投资建议"。严禁任何形式的编造和伪造。
2. **API降级规则**：如实时估值API不可用，必须在播报中明确标注"⚠️ 实时估值不可用，以下基于T-1净值数据提供投资建议"。
3. **数据标注**：每条数据必须标注来源和时间，不可混用实时估值与T-1净值。
4. **异常处理**：API返回异常或超时，不猜测结果，如实报告"数据获取失败"。
- 新浪K线（含均线）：money.finance.sina.com.cn（仅ETF，参数ma=5,10,20,60）

## 十〇、QDII 每日限额基金建仓机制

部分 QDII 基金（如 000834 大成纳斯达克100）有**单日申购限额**（如每日仅限¥10），无法一次性买入计划金额。

### 建仓流程
1. 用户在蚂蚁财富买入时被限额 → 告知 agent 实际可买金额
2. Agent 在 recommended_funds.json 中设置 `status: "building"`，记录每日限额和计划总额
3. 每个交易日（周一至周五），用户在蚂蚁财富手动买入限额金额
4. 每日 14:30 播报自动提醒：`💱 {代码} {名称} — 买入 ¥{限额}（QDII每日限额，已买¥X/计划¥Y）`
5. 用户操作后告知 agent，agent 记录到 pending_transactions
6. 累计买入达到计划总额后，status 更新为 "completed"

### 注意事项
- 周末/节假日不提醒
- 买入记录必须以用户确认为准，不能自动记录
- 限额金额可能变化（平台调整），以用户实际反馈为准
- portfolio.json 的 transactions 中记录每笔小额买入

## 十一、陷阱与教训

1. **东方财富API必须带Referer头**：`Referer: http://fund.eastmoney.com/`，否则返回403或空Data
2. **同一天不要对同一基金既加仓又减仓**：加仓的金额会被减仓操作覆盖（2026-06-29 实际案例：用户先加¥300再减仓40%，¥120被无效操作）
3. **操作顺序很重要**：先减仓再观察，确认后再加仓；不要边加边减
4. **基金T+1**：15:00前提交按当天净值，15:00后按下一交易日。建议14:30-14:50提交减仓操作
5. **AkShare在云服务器安装困难**：用东方财富API+urllib零依赖替代
6. **月收益20%不切实际**：用户曾提出此目标，需主动用数据说明风险（年化240%=巴菲特12倍）
7. **Skill必须存放在全局目录** `/home/ubuntu/.hermes/skills/`，不要放在profile目录下。读取已有skill也应查找全局目录
8. **volatile数据不存memory**：持仓明细、盈亏数据等频繁变化的内容存JSON文件，memory只存稳定偏好
9. **Cron job provider 必须是 "qwen" 不是 "custom"**：cronjob工具会自动捕获当前session的provider为"custom"，但config.yaml中定义的provider key是"qwen"，导致运行时401错误。创建后必须检查并修正。同理，`deliver: "origin"` 会捕获创建时的chat_id，用户换对话后收不到报告，建议用 `deliver: "feishu"` 投递到Home Channel
10. **⚠️ 绝不假设今天是周几**：定投日是周四，但 cron 在周一到周五都运行。记录定投操作前**必须先确认实际星期几**，不能因为看到"定投"相关 prompt 就假设今天是周四。2026-07-02 教训：agent 假设周一是周四，凭空记录了 ¥450 不存在的定投交易。
11. **⚠️ 交易记录必须以用户确认为准**：绝不主动记录用户未确认的交易。用户说"今天买了X"才写入 pending_transactions，不能根据定投计划自动生成交易记录。
12. **⚠️ 截图校准是数据唯一真实来源**：portfolio.json 中的数据可能与实际不符（历史交易记录错误、净值计算偏差等）。每次收到截图时，以截图金额为准全覆盖，不要试图"修复"历史交易来凑数。小额差异（¥50-100）通常是份额四舍五入+净值波动，属于正常误差。
13. **⚠️ 历史交易记录可能不准确**：007817 曾记录了 6/29 减仓 ¥4,460，但用户确认从未减仓。transactions 数组可能包含错误数据，需要定期与截图交叉验证。已实现收益不能仅凭 transactions 计算。
